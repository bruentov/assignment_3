## 1. Conventions shared by all methods

* **Deep DFS.** No recursion anywhere. DFS uses an explicit stack plus a per-vertex arc pointer `ptr[x]`
  (the index of the next unexplored arc of `x`). A suspended vertex therefore resumes exactly where it stopped and
  its neighbours are never rescanned, which keeps DFS at `O(n+m)`. Tested with chains of 100 000 vertices
  (far beyond Python's default recursion limit of 1 000).
* **State reset.** Every function allocates all of its arrays (`parent`, `size`, `visited`, `state`, adjacency, heap…)
  locally and keeps no module-level mutable state; the supplied `main.py` only parses a line, calls a function and prints.
  A mixed batch (all six methods, plus a cyclic and an acyclic request back-to-back) was run three more times in the
  same process and once more through the CLI twice in one process; all outputs were identical to the first pass.
* **Interface.** The supplied adapter calls `algorithms.<task>(request)` with the parsed JSON dict. Each public function is a thin
  wrapper that unpacks `request` and calls a private function (`_dsu`, `_kruskal`, …) taking plain arguments.
* **Edge IDs.** Edge `i` is `edges[i]`. Sorting (Kruskal) sorts *indices*; adjacency arrays (CSR form: `start`, `to`,
  `eid`) store the original ID next to every arc, so IDs survive any reordering.
* **Integers.** Python ints are unbounded, so sums such as `4·10⁹` or `-9.9999·10¹³` cannot overflow.
  Unreachable distances are `None`, which `json.dumps` writes as `null`.

## 2. DSU (`dsu`)

*Steps.* `parent[i]=i`, `size[i]=1`. For each `[u,v]`: find both roots (iterative, two-pass path compression);
if different, attach the smaller tree under the larger (union by size), add sizes, decrement `components`,
update `largest = max(largest, size[new root])`; append `[components, largest]`.

*Invariant.* After every operation the forest `parent` represents exactly the partition generated by the unions so far;
`size[r]` is the number of vertices in the tree of root `r`; `components` = number of roots; `largest` = max size over roots.
A union only changes one component, so `largest` can only change to the new merged size.

*Correctness.* Repeated unions and self-unions find equal roots and change nothing, so the partition (and the state) is
unchanged. Initially `largest=1` for `n>0`, `0` for `n=0`, and no initial state is emitted. Size is maintained separately
from any rank notion (the test "merge two big comps" would break an implementation that confuses rank with size).

*Complexity.* `O(n + q·α(n))` time, `O(n+q)` memory (parent, size, and the `q` returned states).

## 3. Kruskal (`kruskal`)

*Steps.* Sort edge indices by weight; scan them; accept edge `i` when `find(u) != find(v)` and union.
Result: `cost` = sum of accepted weights, `edge_ids` = accepted IDs, `components = n − (#accepted)`.

*Invariant.* The accepted edges form a forest that is contained in some minimum spanning forest (cut/exchange argument);
DSU components equal the components of the accepted set.

*Correctness.* An edge is rejected only if its endpoints are already connected by lighter-or-equal accepted edges, so
it is a heaviest edge on some cycle and is not needed. A self-loop always has `find(u)==find(v)` and is never
accepted. Negative weights need no special handling (only the order matters). Each component ends with exactly
`size−1` edges, so the total is `n−c`.

*Boundary cases tested.* `n=0` → `cost=0, edge_ids=[], components=0`; isolates (`n=3`, no edges → 3 components);
negative self-loops ignored; parallel edges (cheaper one chosen); total `4·10⁹` and `−3·10⁹` (beyond 32 bits).

*Complexity.* `O(n + m log(m+1))` time, `O(n+m)` memory.

## 4. Prim (`prim`)

*Steps.* Build CSR adjacency (skipping self-loops). For every unvisited start vertex `s` (a new component):
mark it, push its arcs `(weight, edge_id, neighbour)` into a binary heap, then repeatedly pop the lightest arc; if the
neighbour is unvisited, mark it, accept the edge, and push the neighbour's arcs to unvisited vertices (lazy deletion).

*Invariant.* The accepted edges are a minimum spanning tree of the visited part of the current component; the heap
contains every arc leaving the visited set (plus stale arcs to already visited vertices that are skipped).

*Correctness.* Cut property: the lightest arc crossing (visited, unvisited) belongs to some MST. Restarting from the next
unvisited vertex yields one tree per component, so `components` is incremented once per start. Ties are broken by edge ID
(tuple comparison), which only makes the output deterministic; any optimum is accepted.

*Complexity.* `O(n + m log(m+1))` with a lazy heap, `O(n+m)` memory. Kruskal and Prim return the same `cost` and
`components` on every test, including 400 random instances checked against a brute-force optimum and on large random graphs.

## 5. SCC – Kosaraju (`scc`)

*Steps.* (1) Iterative DFS on `G`; push a vertex on `finish` when all its arcs are done. (2) Build the transpose.
(3) Process vertices in *decreasing* finish order; each unlabeled vertex starts an iterative DFS in `Gᵀ` that labels
everything it reaches with a fresh label. (4) Condensation: for every edge `u→v` with different labels add the pair
`(label[u], label[v])` once, de-duplicated with a hash set (`a*k+b` as integer key).

*Invariant / correctness.* The vertex with the latest finish time in `G` lies in a source SCC of the condensation;
its DFS in `Gᵀ` cannot leave that SCC, so it labels exactly that SCC. Removing it, the argument repeats.
Equal labels ⇔ mutual reachability. Isolated vertices form singleton SCCs; self-loops and duplicate edges never
create internal or duplicate condensation pairs.

*Boundary cases tested.* `n=0` (both arrays empty), isolates, self-loop with duplicated cross edges (exactly one
condensation pair), 1e5-vertex chain (100 000 SCCs, 99 999 condensation pairs) and 1e5-vertex ring (one SCC).
Random graphs are verified against an independently written iterative **Tarjan** implementation (same partition,
identical condensation edge set).

*Complexity.* `O(n+m)` expected time (hash set), `O(n+m)` memory.

## 6. Topological order (`topo`)

*Steps.* Iterative DFS with states 0 = unvisited, 1 = active (on the stack), 2 = finished. On arc `x→y`:
`state[y]==1` → return `acyclic=false, order=[]` (a self-loop is such an arc, `y==x` is active);
`state[y]==0` → push `y`; `state[y]==2` → ignore. When all arcs of `x` are done, set state 2 and append to `finish`.
All components are started in the outer loop. If no cycle, `order = reversed(finish)`.

*Invariant.* The active vertices form the current DFS path; an arc into the path closes a directed cycle.
Conversely, if a cycle exists, the first vertex of it that is entered has all other cycle vertices reachable through it,
and the DFS reaches the arc that closes it while that vertex is still active.

*Correctness of the order.* For an arc `u→v` in an acyclic graph, `v` finishes before `u`, so after reversal `u` precedes `v`.
An arc to a finished vertex is *not* a cycle (tested with a diamond plus a shortcut edge plus a duplicate edge).

*Boundary cases tested.* `n=0` → `acyclic=true, order=[]`; self-loop; 2-cycle; cycle in a later component; 1e5 chain
(order must be `0..n-1`), reversed 1e5 chain, and a 1e5 ring (cycle found at depth 1e5).

*Complexity.* `O(n+m)` time and memory.

## 7. DAG shortest paths (`dag`)

*Steps.* Run `topo` on the **whole** graph first, so a cycle anywhere (even unreachable from `source`) gives
`acyclic=false, distance=[], parent_edge=[]`. Otherwise set `dist[source]=0`, then walk the topological order; for each
vertex whose `dist` is not `None`, relax every outgoing arc `x→y` with `dist[x]+w < dist[y]` (or `dist[y]` is `None`)
and store the **edge ID** in `parent_edge[y]`.

*Invariant.* When `x` is reached in the order, all its predecessors have been processed, so `dist[x]` is final.
Unreachable vertices are never used to relax, so a negative edge out of an unreachable vertex cannot create a fake
distance (test: edge `1→2` of weight −100 is ignored). `None`, not `−1`, marks unreachable; a distance of −1 is a valid
finite value (test `[0,-1,-2]`).

*Correctness of parents.* `parent_edge[y]=i` is set only together with `dist[y]=dist[tail(i)]+w(i)`, and `dist[tail]` is
final, so every parent edge ends at its vertex, is tight, and following parents strictly decreases topological position
until the source (whose entry is `-1`) is reached. This is exactly what `check_dag` in `tests/checkers.py` verifies.

*Complexity.* `O(n+m)` time and memory.

### Route helper

`route(source, target, parent_edge, edges)` follows `parent_edge[v]` back to `source` (taking `edges[i][0]` as the
predecessor) and reverses the list; `O(L)` time and space. **No-route convention: it returns the empty list `[]`**
(only the helper does this; the JSON `distance` still uses `null`). The route to the source is `[source]`.

Actual calls (spec example, `edges=[[0,1,3],[0,2,8],[1,2,-7],[2,3,4]]`, `source=0`;
`dag` returned `distance=[0,3,-4,0,null]`, `parent_edge=[-1,0,2,3,-1]`):

| call | result | selected edge IDs | direction / weight check |
|---|---|---|---|
| `route(0,3,pe,edges)` | `[0,1,2,3]` | `0, 2, 3` | `0→1→2→3`; 3 + (−7) + 4 = **0** = `distance[3]` |
| `route(0,0,pe,edges)` | `[0]` | – | source |
| `route(0,4,pe,edges)` | `[]` | – | vertex 4 unreachable |

Tied / parallel edges: `edges=[[0,1,5],[0,1,5],[0,2,1],[2,1,4]]`, `source=0`. Vertex 1 has three tied shortest routes of cost 5
(parallel edges 0 and 1, and `0→2→1` = 1+4). The solution returned `distance=[0,5,1]`,
`parent_edge=[-1,0,2]`, `route(0,1,…)=[0,1]` using edge ID 0 (relaxation uses strict `<`, so the first tied edge in adjacency
order wins). With the same edges listed in another order, `[[0,2,1],[2,1,4],[0,1,5],[0,1,5]]`, the solution returned
`parent_edge=[-1,2,0]` – a different but equally valid answer (edge 2 is `0→1`, cost 5); the route is again `[0,1]`.
The semantic checker accepts both.

## 9. Benchmark: Kruskal vs Prim

* **Graphs:** random multigraphs (self-loops and parallel edges allowed), weights uniform in `[−10⁹, 10⁹]`, generated by
  `random.Random(12345 + n)`; **the same edge list is given to both methods**. Reproduce: `python tools/benchmark.py`
  (stored results: `tests/benchmark_results.json`, `tests/benchmark_output.txt`).
* **Correctness first:** for each size, Kruskal's and Prim's `cost` and `components` agreed, and both outputs passed the
  forest-feasibility checker (valid acyclic forest, `n−c` edges, cost equals sum of weights) before timing.
* **Method:** one untimed warm-up run per method per size, then 5 timed runs each, alternating Kruskal / Prim;
  `time.perf_counter()`; median reported. Python 3.12.3 CPython, Linux x86_64 (kernel 6.18.44), Intel Xeon @ 2.10 GHz,
  1 visible core, 4 GB RAM (a shared cloud sandbox, not a dedicated machine). No compilation step exists in Python.
* **Timing boundary (identical for both):** includes everything inside the function call (sorting / adjacency construction /
  DSU or heap work); excludes graph generation, JSON parsing and output printing. Garbage collection was left at its default.

| n | m | Kruskal runs (s) | Kruskal median (s) | Prim runs (s) | Prim median (s) | components | MSF cost |
|---|---|---|---|---|---|---|---|
| 10 000 | 25 000 | 0.0223, 0.0230, 0.0241, 0.0216, 0.0230 | **0.0230** | 0.0535, 0.0512, 0.0509, 0.0508, 0.0537 | **0.0512** | 72 | −5 361 525 623 924 |
| 50 000 | 125 000 | 0.2007, 0.2041, 0.2006, 0.2017, 0.1885 | **0.2007** | 0.4969, 0.5146, 0.5368, 0.5422, 0.4635 | **0.5146** | 344 | −26 357 594 047 557 |
| 100 000 | 250 000 | 0.5254, 0.4878, 0.4893, 0.5294, 0.4890 | **0.4893** | 1.4722, 1.4418, 1.3940, 1.3305, 1.4145 | **1.4145** | 658 | −52 749 763 734 876 |

**Observations (measured).** Kruskal was faster than Prim at all three sizes: by a factor of 2.23 (10k), 2.56 (50k) and 2.89 (100k)
in the medians. Going from n=10⁴ to n=10⁵ (10× larger input) Kruskal's median grew ×21 and Prim's ×28.
An earlier run of the same script on the same sandbox gave n=10⁵ medians of 0.43 s (Kruskal) and 1.09 s (Prim): the ordering and
the roughly 2.5× gap were the same, but absolute times drifted by up to ~30 % between runs.

**Interpretation (not proven by these runs).** Both algorithms are `O(m log m)`, so the asymptotic bounds do not separate them;
the gap is a constant-factor effect. A plausible explanation is that Prim builds an adjacency structure for `2m` arcs and
performs up to `2m` heap pushes of 3-tuples (Python-level comparisons), while Kruskal performs one C-level sort of `m`
integers with a key and then near-constant-time DSU operations. The faster-than-linear growth is consistent with the `log` factor
and with worse cache behaviour on larger arrays, but I did not profile it to confirm.

**Limitations.** One graph family (sparse random, average degree 5, so the graph is nearly but not fully connected); one seed per size;
only 5 repetitions on a shared single-core machine (run-to-run drift of up to ~30 % between whole benchmark runs, see above);
results are for CPython and would differ in Java/C++ or with an indexed heap or dense graphs, where Prim often does better;
memory was not measured (only the `O(n+m)` analytical bound is claimed).
